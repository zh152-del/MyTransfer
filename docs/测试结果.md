### 一个必须说清楚的前提

自动化用例里，模拟 iPhone 是用 `127.0.0.1` 回环地址连的服务端，
**所以下面的速度是「本机磁盘 + 本机协议栈」的上限，不是 iPhone 实际能拿到的 Wi-Fi 速度**。
真机上速度会受 Wi-Fi、iPhone 端下载节奏、iOS 对快捷指令的调度影响，通常远低于这个值。

| `--lie`（iPhone 谎报字节数 +12345） | `error` | `error` ✓ | `验证失败：iPhone 回报 524300345 字节，源文件 524288000 字节` |

查下来是我测试脚本自己的锅——`parse_qs` 返回的是列表，`urlencode()` 默认 `doseq=False`

已修成 `urlencode(q, doseq=True)`，现在报的是真实注入值 `524300345`。

断点处的接收文件是残的（`.part` 不会转正），这是设计如此：传完才正式命名，
所以断线时 `/recv` 里留的 `*.part` 残片可以随手删。

## 五、Bonjour / mDNS：真的在广播

`tools/probe_mdns.py` 直接往 `224.0.0.251:5353` 发标准 mDNS 查询（`_services._dns-sd._udp.local`
和 `MyTransfer._http._tcp.local`），看有没有人回：

```
已查询 MyTransfer._http._tcp.local
  ✓ 收到回应（来自 192.168.0.199:5353），包头 answer/ns/authority/additional = (0, 0, 3, 0)
  ✓ 回应里带 TXT：port=8765
```

`additional` 里 3 条记录 = PTR（`MyTransfer._http._tcp.local`）+ SRV（`MyTransfer.local:8765`）+ TXT（`port=8765`），
**这正是 iOS 解析 `MyTransfer.local` 需要的全部信息**。连测 4 次都拿到了这个回包。

两点如实说明：

1. **本机探针偶尔会「3 秒没回应」**。原因是本机 5353 同时被 Windows 的
   Apple Bonjour 服务（`svchost -k NetworkService`）占着，Windows 把自己发出的组播只递给其中一个 socket，
   有时递给了 Bonjour 那个。这是同机自测的坑；iPhone 的查询是从网卡进来的（不走回环），
   会递给所有绑定 5353 的 socket，不受这个影响。
2. **Windows 自己不解析 `.local`**（`getaddrinfo("MyTransfer.local")` 在本机直接报 `gaierror 11001`），
   所以自动化测试一律用 `127.0.0.1`；iPhone 的 mDNS 解析器认 `.local`，快捷指令里写
   `http://MyTransfer.local:8765/hello` 就行。

顺手加了两处抗丢包的改动：开机 0.3/1.2/3/6 秒连播之后，**每 20 秒再重播一次**；
查询包带 QU 位（「宁可你单播回我」，iOS 解析已知名字时也会这么查）时，走**单播回包**。

## 七、方案 C 新接口 `GET /url?w=`：按快捷指令的真实顺序验一遍

为了绕开「iOS 动作库里搜不到 JSON、拿到变量也拆不了文字」这两个坑（见《iPhone 快捷指令.md》），
电脑端新加了 `GET /url?w=name|file|done|fail`，**每个字段各问一次、只回一行**。
`tools/url_flow.py` 就按 iPhone 上那 6 个动作的顺序，一个一个请求过去：

| 快捷指令动作 | 对应请求 | 实测返回（300MB） |
|-------------|---------|-----------------|
| 1. 获取URL内容（文件名） | `GET /url?w=name` | `测试300MB.bin` |
| 2. 获取URL内容（下载地址） | `GET /url?w=file` | `http://192.168.0.199:8791/file/da4864d8` |
| 3. 获取URL内容（用上一个动作的输出，类型=文件） | 真下载 | 收 314572800 字节 / 1.25 秒 |
| 4. 获取URL内容（回报） | `GET /url?w=done` | `接收完成，已回报 314572800 字节`，**服务端同时 `state = done`** |
| 5. 任务结束后再问 `?w=fail` | — | 返回空（任务已结束，不该再报失败） |
| 6. `?w=乱填` | 百分号编码后请求 | `w=name|file|done|fail`（提示串，不静默） |

单独一个场景验失败入口（新起一个服务端，字节还没发完就问 `w=fail`）：
返回 `已报告失败`，服务端 `state = error` ✓

### 又抓到一个：方案 C 原本会少交一次「回报」

按快捷指令真实顺序跑通之后回头看，原设计的 6 步是**闭环不了的**：
`w=done` 只负责把回报地址吐出来，手机上还得再拿这个地址去「获取一次」才算真回报——
也就是**文档少写了一个动作**，而真机上这一步恰好是最容易插错的地方
（用户截图里就是把它插成了「上一个动作 = 保存文件的输出」，一条文件对象塞进网址格，直接报错）。

修法：把 `?w=done` 改成**问一次就自己把事办了**——字节已发完就直接完成回报
（内部调 `finish(t.size)`，走的还是老 `/done` 那条路，校验逻辑一点没改）；
只有字节还没发完（iPhone 抢跑）时才退回吐地址。
`?w=fail` 同理，直接把任务判成 `error`。

这样 6 步真的闭环，`w=done` 回一句话就完事，手机上不用再多一个「用上一个动作的输出去获取」的动作。

**改完必须重启电脑端程序**（双击桌面那个 bat），这条前面说过了，这里再提一次。

500MB 同一套流程也全过：收 524288000 字节 / 1.99 秒，落盘 SHA256 与源一致，`state = done`。

### 这一轮抓到并修掉的一个真 bug（值得记下来）

第一版跑测试时，第 4 步「取回报地址」返回的是**空字符串**，第 5 步返回的是提示串，第 6 步直接崩。
按快捷指令的真实顺序跑，才把它暴露出来：

- 文件字节发完之后，服务端状态机进的是 `verifying`（「已发完，等 iPhone 回报字节数」），
  而 `_one_field()` 的可用状态白名单只写了 `waiting / ready / transferring`，**漏了 `verifying`**；
- 快捷指令恰恰是**下载完之后**才去问回报地址的 —— 也就是服务端正在 `verifying` 的时候。
  真人一眼看代码不容易发现，因为静态看「有任务就能查」是成立的。

修法：新增常量 `LIVE_STATES = (waiting, ready, transferring, verifying)`，两处查询统一用它；
同时给 `_done()` 加了幂等（已经回报过一次的 `done` 不再重复走一遍 `finish()`，避免重复记账）。
**这个 bug 只有在「按手机实际动作顺序」跑才会碰到，纯跑服务端单测查不出来。**

### 没有任务时的空返回

电脑还没选文件时，`?w=name / ?w=file` 都返回**零长度**（不是错误、不是占位符），
手机上「获取URL内容」拿到空值会自己报错停下，不会拿空地址去下载。实测返回体长度 = 0。

## 十、每一步请求都看得见（逐步日志，2026-10-05）

### 为什么要加

真机跑的时候，日志里**只有 `[第 1 步 取文件名]`，从第二步开始一条都没有**。
当时看不出两件关键的事：请求到底有没有出手机、出了的话网址长什么样。
所以把「每个请求是不是到了服务器」做成显式日志。

### 加了什么

| 位置 | 内容 |
|------|------|
| `do_GET` 入口 | `收到请求 <完整path>  ← <手机IP>（<User-Agent>）  [<第 N 步 名称>]` |
| `_text` / `_json` | `应答 <code>，<N> 字节：<回给手机的内容>` |
| `_tag()` | 把 `?w=xxx` / `/file/<id>` 翻译成「第 N 步」，认不出的地址直接标注「多半是快捷指令里网址手打错了」 |
| `MyTransfer.py` | 启动时把日志按原样落一份到 `logs/server_<时间戳>.log` |

同时删掉了三条被新日志完全覆盖的旧行（`iPhone 询问服务信息` / `iPhone 取字段` / `iPhone 询问纯文本信息`），
一条请求固定两行，不刷屏。

### 顺手加的容错

| 改动 | 结果 |
|------|------|
| `?W=FILE` 大写 | 认，正常返回下载地址（回归用例 `[2b]` 覆盖） |

## 第十一节 真凶：mDNS 应答器两个硬 bug，导致 iPhone「请求超时」（2026-10-06）

### 背景
用户手打端口 `http://MyTransfer.local:8765/...` 后，iPhone 仍然「请求超时」。
之前一直以为是「缺 A 记录」，加完 A 记录还没好——原因是应答器根本就没在答。

### 两个 bug（都在 `mt_server.py` 的 `MdnsResponder`）

1. **名字读错（最致命）**：问句里的域名是「1 字节长度 + 标签」结构（`MyTransfer\x05local\x00`），
   老代码却 `data[i:end].decode()` 直接当纯文本读，于是 `MyTransfer.local` 被读成
   `MyTransfer\x05local`，**所有匹配分支永远不成立——我们的 mDNS 其实一次查询都没回答过**，
   只能靠往外广播、让 iPhone 偶发撞上（这解释了为什么有时能到、有时超时）。

2. **报文拼错**：`_reply_addr` / `_reply` 把「问题段」只写了域名、漏了 `QTYPE/QCLASS` 这 4 字节，
   还在答案前面多塞了一个名字，整包字节错位，iPhone 拿到也解析不了（实测 an=0、记录掉进 authority 段）。

### 修复
- 新增 `dec_name()` 正确解码 DNS 名字（长度前缀 → 带点字符串）。
- 重写 `_build()` / `_rr_a` / `_rr_ptr` / `_rr_srv` / `_rr_txt`，严格按标准 DNS 报文字节对齐：
  问题段 = 名字 + QTYPE + QCLASS；答案段 = 每条 RR（名字 + type + class + ttl + rdlen + rdata）。
- 现在同时答：**A 记录**（MyTransfer.local → 本机 IP）、**PTR/SRV/TXT**（服务端口），
  并把这些一并塞进主动公告，iPhone 一次拿全，不再来回问两轮。

### 验证（全离线，不发包）
`logs/_dev/verify_mdns_offline.py` 用假 socket 截获 `_answer` 会发出的字节再解析回来：

| 查询 | 结果 |
|------|------|
| A 记录查询 `MyTransfer.local` | `an=1`，A → `192.168.0.199` ✓ |
| SRV 查询 `MyTransfer._http._tcp.local` | `an=4`：A+PTR+SRV+TXT 齐全 ✓ |
| 主动公告（无问题段） | `qd=0 an=4` 齐全（含 A）✓ |

### 注意
- 之前的排障探针（`probe_a.py` / `probe_apple.py` / `probe_recv.py`）曾往 `224.0.0.251` 多发了包，
  被沙箱当成网络行为掐了网；这类**发往网络的探针不要再跑**。后续一律用离线方式验证 mDNS。
- 真机复验交给用户：重启电脑端（双击桌面 `MyTransfer.bat`），在 iPhone 上跑一次「接收电脑文件」，
  看 PC 日志首行 `Bonjour 广播：MyTransfer.local -> 192.168.0.199（含 A 记录 + 服务记录）`，
  以及每一步请求是否都到；若仍超时再核对同一 Wi-Fi / 访客隔离。
